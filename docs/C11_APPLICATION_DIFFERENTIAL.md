# PR #79 — application-level C++ vs C11 Owner differential

Status: **source-only qualification, not production replacement**. Keep [PR #79](https://github.com/qigao/praktor/pull/79) Draft and the current C++ `WorkflowExecutor` in production. [macOS Legacy Shell #81](https://github.com/qigao/praktor/issues/81) remains Open. Neither a successful same-commit rerun nor this new test is a fix for #81.

## Same-input two-engine qualification

`praktor/test/workflow_owner_differential_test.cpp` feeds the **same literal YAML bytes** to the existing production `TaskParser::parseText()` → `WorkflowRunner` → C++ `WorkflowExecutor`, and independently to:

```
praktor_workflow_snapshot_create_inline()
  -> workflow_dag_state / task_registry
  -> task-local workflow_load_task_text_scope()
  -> orch_session_plan_create() / native_host / session_tick()
  -> CFlow ManualExecutor run/cancel/finalize acknowledgment
  -> selected-output transaction + staged typed TaskRegistry publication
  -> Process-retainer drain preflight
  -> owner-side TaskRegistry + DAG terminal settlement
```

There is **no application-backend selector** in the native path, no C++ `DeclarativeTreeExecutor` delegation and no automatic Legacy fallback. Both executions use a deterministic single-driver admission width of one; that is the only order in which a strict start-sequence comparison is meaningful.

The test records actual production `TaskStarted` observer events, not declaration order or sorted output dictionaries. The native trace records only tasks actually reserved by the canonical C11 DAG. The comparison selects contractually stable task status, declared text output, overall workflow status and terminal dependency admission. Timing metadata, logging and autogenerated/internal output fields are not presumed equal.

## Current implemented cases

| Case | Comparison / evidence | Scope |
| --- | --- | --- |
| Ordered success | `prepare` → `verify` admission, status, selected `observed` / `finished` values, 2/2 owner-side completion | Independent C11 task Session and CFlow owner, no native subprocess |
| Ordinary failure | Missing `CheckExitCode` input fails `reject`; `downstream` must never receive a TaskStarted/native claim; failed terminal | Error class and failed-task status; raw error strings and internal failure metadata still require differential work |
| Pre-start cancellation | A pre-cancelled C++ ExecutionControl vs a C11 DAG external stop both block the first task; no selected outputs | NOT in-flight cancellation parity |
| Lifetime barrier | Each admitted C11 tick runs/finalizes once, Owner observes an idle CFlow and zero outstanding Process reservations before publication or release | An empty retainer is not a real NativeIO/OS child lease test |

Selected output JSON in this narrow corpus is intentionally limited to unescaped ASCII word text; unsupported text/typed conversion **fails admission** instead of claiming a general WorkflowValue projection. Cross-task output visibility and typed/numeric JSON parity remain separate gates. No source-only test is permission to remove the production C++ context or its adapters.

## Mandatory expansion before switch discussion

1. **Schema/input corpus:** load representative, identical on-disk YAML with inputs/variables, environment, nested actions, input contracts, observable events, runtime error code/phase and output types. Compare exact declared outputs and normalized redaction-safe diagnostics; record intentional differences explicitly rather than weakening assertions.
2. **Lifecycle corpus:** real Shell/NativeIO, timeout, in-flight cancel, Close overlapping Process completion, lease transfer, output suppression after failed/cancelled tasks and no use-after-free. Use actual PIDs, exit status/signals, cancellation generations and one-settle/one-close evidence. Diagnose the independently tracked macOS signatures in #81, including both exit 137 and cancellation-state mismatches.
3. **DAG corpus:** failures, capacity admission, conflicts, timeout, cascaded cancellation, reserved-vs-published outputs and terminal DAG status, with both serial and admitted multi-worker cases.
4. **Parallel corpus:** independent bounded **per-worker** Process retainer or an explicit serialized arbiter; atomic group commit only after every callback finalizes and each Process recovery owner drains. Inject conflict, capacity, cancellation/close overlap and native recovery failure; poison-on-error remains fail-closed.
5. **CI acceptance:** exact-HEAD Native SDK Linux/Windows/macOS, Android package/installed C consumer, lifecycle ASan/UBSan, unsuppressed full-source TSan and deterministic repeat/failed-run evidence. Require this differential target to be selected in TSan; do not classify source-only success as whole-program parity.
6. **Final cutover gate:** only after full supported actions, DAG scheduler, WorkflowContext, SDK/CLI, C11 ownership and platform tests have proven application parity may C++ backend deletion and production switch be considered.

## Fail-closed constraints

The source-only C11 Session is single-driver; CFlow callback completion **does not** imply Session SUCCESS. A `RUNNING` Session may not publish or retire a task merely because its callback finalized. Failure/cancellation never admits a dependent task or manufactures a success value. The root value store/TaskRegistry/DAG remain exclusively modified by the application Owner, not worker callbacks. A live retainer or unacknowledged native completion blocks publication.

This document defines a qualification gate, **not a claim that CI is green**. Evidence must be tied to the final pushed head and each actual platform/job attempt.
